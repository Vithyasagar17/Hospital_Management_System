# Phase 3 Upgrade — Notifications, Search & Auditability

Phase 3 builds on the Phase 2 clinical workflow and adds a production-style activity layer.

## 1. Notification Center

Every authenticated user now has a notification bell in the top bar and a full notification center.

Notifications are generated by real workflow actions, including:
- Patient books an appointment → doctor is notified.
- Doctor confirms/completes/cancels an appointment → patient is notified.
- Patient cancels an appointment → doctor is notified.
- Doctor creates a prescription → patient is notified.
- Admin blacklists/restores an account → that user is notified.
- New self-registration → admins are notified.

Notifications support unread/read state, open-to-related-record behavior, and mark-all-read.

## 2. Advanced Search & Filters

Admin:
- Universal search across doctors, patients and appointments.
- Doctor filters: name, specialization, active/blacklisted.
- Patient filters: name/contact/address, age range, active/blacklisted.
- Appointment filters: doctor/patient/reason, workflow status and date range.

Doctor:
- Appointment filters by patient/reason/status/date.
- Patient directory search by name/contact/address.
- Prescription filters by patient/diagnosis/date.

Patient:
- Appointment filters by doctor/reason/status/date.
- Doctor discovery by name/specialization.
- Optional "Available on" date filter that only returns doctors with real free slots.

## 3. Audit Log

A new Admin-only Audit Logs screen records meaningful actions with:
- timestamp
- actor username
- role
- action
- entity type/id
- human-readable description

Logged actions include login/logout, registration, profile changes, account controls, appointment booking/cancellation/status changes, clinical notes, prescriptions, medicines, and doctor availability changes.

## Database Compatibility

Phase 3 is additive. Existing Phase 2 `instance/hms.db` files are upgraded automatically by creating the new `notification` and `audit_log` tables if they do not exist. No database reset is required.

`python create_db.py` is still an explicit RESET operation. It rebuilds the entire demo database and seeds Phase 3 demo activity.

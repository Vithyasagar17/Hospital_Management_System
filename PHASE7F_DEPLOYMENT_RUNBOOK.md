# Phase 7F — Production Deployment & Release Runbook

Phase 7F turns the Phase 7A–7E stack into a production deployment definition.
The included `render.yaml` targets Render in the Singapore region with managed
PostgreSQL, managed Redis-compatible Key Value, a Docker web service, a Celery
worker, and a separate Celery Beat service.

## Production topology

```text
Internet / HTTPS
       |
       v
Render Web Service
Gunicorn + Flask
       |
       +-------------------+
       |                   |
       v                   v
Managed PostgreSQL    Render Key Value
       ^                   ^
       |                   |
       +---------+---------+
                 |
        +--------+--------+
        |                 |
  Celery Worker       Celery Beat
```

Render terminates HTTPS for the public web service. PostgreSQL and Key Value use
private service connection strings and block public inbound access in the
Blueprint.

## Why the production database is not the local Docker database

The local Docker volumes are development infrastructure. Phase 7F provisions
new managed production resources. Do not upload `instance/hms.db` and do not
copy the local Docker PostgreSQL volume into production.

Start production with a fresh database unless you explicitly plan and test a
data migration.

## Deployment prerequisites

Before deployment, all of the following should be true:

```powershell
python -m pytest -q
git diff --check
docker compose config
docker compose ps
```

The Phase 7D GitHub Actions checks should also be green on the commit you intend
to merge to `main`.

Commit Phase 7F on the feature branch, open a pull request into `main`, let CI
pass, then merge.

## Create the Render Blueprint

1. Push `render.yaml` to `main`.
2. In Render, choose **New > Blueprint**.
3. Connect the GitHub repository containing this file.
4. Render will discover the Blueprint.
5. Review the four services/resources before creating them.

The Blueprint intentionally uses paid entry-level plans because production
requires always-on workers, persistent Key Value storage, and the web
`preDeployCommand` used for safe database migrations.

Resources:

```text
medora-web       Docker web service
medora-worker    Celery background worker
medora-beat      Celery Beat scheduler
medora-postgres  Managed PostgreSQL 16
medora-kv        Managed Redis-compatible Key Value / Valkey
```

All resources are placed in `singapore`.

## Database migration strategy

The local Docker entrypoint can migrate automatically, but production disables
that behavior:

```text
HMS_RUN_MIGRATIONS=0
```

Only the web service owns release migrations through:

```text
preDeployCommand:
python -m flask --app run db upgrade
```

This prevents `web`, `worker`, and `beat` from racing to run Alembic at the same
time.

If the pre-deploy migration fails, do not force the deployment. Inspect the
migration error, fix the migration, run CI again, and redeploy.

## Production secrets

`HMS_SECRET_KEY` is generated by Render for the web service. The worker and Beat
also receive generated secrets because the existing production environment
validator requires a strong secret in every container.

Never commit SMTP passwords, provider tokens, or production credentials to Git.

If real email is required, configure these in the Render dashboard for the
services that send email:

```text
HMS_MAIL_MODE=smtp
HMS_SMTP_SERVER=...
HMS_SMTP_PORT=587
HMS_SMTP_USERNAME=...
HMS_SMTP_PASSWORD=...
HMS_SMTP_FROM=...
HMS_SMTP_USE_TLS=1
HMS_SMTP_USE_SSL=0
```

The Celery worker needs the SMTP values if appointment reminder email is enabled.

Then set:

```text
HMS_BACKGROUND_SEND_REMINDER_EMAILS=1
```

on `medora-worker`.

## First production Admin

The production database starts empty except for the schema.

After the first successful deploy, open a Shell for `medora-web` and run:

```bash
HMS_BOOTSTRAP_ADMIN_PASSWORD='use-a-new-strong-password' python docker/bootstrap_admin.py
```

Optional:

```bash
HMS_BOOTSTRAP_ADMIN_USERNAME='admin' HMS_BOOTSTRAP_ADMIN_EMAIL='your-email@example.com' HMS_BOOTSTRAP_ADMIN_PASSWORD='use-a-new-strong-password' python docker/bootstrap_admin.py
```

Do not use the old local development Admin password.

## Smoke verification

After Render reports the web service healthy, copy its HTTPS URL and run:

```powershell
python scripts/verify_deployment.py https://YOUR-SERVICE.onrender.com
```

The verifier checks:

- HTTPS is being used.
- `/health/live` returns 200.
- `/health/ready` returns ready.
- PostgreSQL is healthy.
- Key Value is healthy.
- `X-Request-ID` round-trips correctly.
- `/metrics` is either intentionally disabled or reachable.

The Blueprint disables public metrics by default:

```text
HMS_METRICS_ENABLED=0
```

Structured logs and health endpoints remain enabled.

## Manual production checks

Open:

```text
https://YOUR-SERVICE.onrender.com/health/live
https://YOUR-SERVICE.onrender.com/health/ready
```

Then verify in Render logs:

```text
medora-web       Gunicorn workers booted
medora-worker    celery@... ready
medora-beat      beat scheduler started
```

Verify the worker has:

```text
medora.appointment_reminders
medora.waitlist_maintenance
medora.send_email
```

registered.

## Custom domain and HTTPS

The initial `onrender.com` domain already uses HTTPS.

When you own a production domain, add it to `medora-web` in Render, create the
DNS records Render provides, wait for verification, and verify the application
again using the custom `https://` URL.

Keep:

```text
HMS_COOKIE_SECURE=1
```

in production.

## Release process

Recommended release flow:

```text
feature branch
      |
      v
Pull Request
      |
      v
Phase 7D CI
 tests + migrations + Docker build
      |
      v
merge to main
      |
      +--> GitHub container release artifact
      |
      +--> Render auto-deploy after checks pass
               |
               v
        pre-deploy Alembic upgrade
               |
               v
          web / worker / beat
```

The Blueprint uses:

```text
autoDeployTrigger: checksPass
```

so Render deploys a Git-linked service only after the linked commit's checks
pass.

## Rollback policy

Application rollback and database rollback are deliberately separate.

### Application failure without a schema incompatibility

Use Render's deploy history to redeploy the last known-good application commit.
Do not downgrade the database merely because application code is being rolled
back.

### Migration failure before deployment

The pre-deploy command prevents the new web release from starting. Fix the
migration and deploy again.

### Migration succeeded but new code is faulty

Prefer a backward-compatible migration policy:

1. Roll back the application to the previous known-good deploy.
2. Leave the database at the newer Alembic revision if the old application can
   still operate against it.
3. Fix the application and redeploy.

### Destructive/incompatible migration

Before any migration that drops/renames data or changes meaning:

1. Create/confirm a managed database backup or restore point.
2. Use an expand-and-contract migration across multiple releases.
3. Test restore behavior.
4. Prepare a documented data rollback plan.

Do not rely on `flask db downgrade` as the primary production disaster-recovery
strategy.

## Backup and recovery

Use the managed PostgreSQL backup/PITR capabilities provided by the selected
plan and verify them before storing important production data.

A backup is not considered complete until restore has been tested.

For Redis/Key Value, queued Celery jobs should be treated as recoverable
operational state, not the source of truth. PostgreSQL remains the durable HMS
system of record.

## Scaling

Start with one instance each:

```text
medora-web       1
medora-worker    1
medora-beat      1
```

Never run multiple Beat schedulers unless distributed scheduler locking is
introduced, because duplicate Beat instances can enqueue duplicate periodic
jobs.

The application-level reminder idempotency protects reminder records, but a
single Beat remains the correct operational design.

Web/worker capacity can be increased later based on observed latency, queue
depth, and database capacity.

## Production security checklist

Before using real data:

- `HMS_ENV=production`
- `HMS_COOKIE_SECURE=1`
- strong generated `HMS_SECRET_KEY`
- managed PostgreSQL uses private access
- managed Key Value uses private access
- no `.env` or credentials committed
- real SMTP credentials stored only as Render secrets
- `/metrics` disabled publicly unless protected
- CI required before merge/deploy
- Admin bootstrap password rotated and not reused
- custom domain HTTPS verified if a custom domain is used
- production backups and restore procedure verified
